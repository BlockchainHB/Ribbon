Source study / 20 October 2026 / 17 repositories

A scrolling Mac window manager.
Feasible. Native. Rust is optional.

For a Rust-based product, the best starting hypothesis is a Rust background engine with a SwiftUI/AppKit interface. Paneru is the closest existing foundation; Rift is the second Rust candidate. A fresh implementation entirely in Swift is also credible.

The main performance risk is cross-process window control. Layout arithmetic is only one step. Responsiveness also depends on AX calls, the target application's behavior, frame scheduling, stale-event handling and macOS screen constraints. This review establishes architecture choices, not a fastest-language benchmark.

01 / Decision

What does “fastest” mean?

Fastest route using existing Rust

Evaluate Paneru first. Add a native settings and onboarding shell after validating its engine on real windows. Keep hotkeys, gesture processing and animation inside the engine.

Fastest fresh Mac-only build

Swift with AppKit and SwiftUI likely reduces bridging, build and packaging work. OmniWM, Nehir, Defi and AeroSpace demonstrate viable native architecture.

Fastest runtime

Undetermined without comparable release builds on the same hardware. Rust is a strong systems choice; source language alone does not establish lower input-to-visible latency.

ChainYourMac's own product page describes a Rust engine and SwiftUI app. The feature scope includes a strip per display and native Space, stacking and tabs, gestures, pinned columns, settings, persistence and recovery. Its implementation was not available for this review.

Closest match

paneru

2,411 stars

Rust + Bevy ECS · MIT

The closest existing Rust foundation: persistent horizontal strips, stacks, tabbed display, raw gestures, inertia, session restore and native Spaces. Layout state and OS frame commits are separate systems; IPC currently uses typed Mach messages.

The current frame commit systems use parallel worker iteration. The architecture document's blanket main-thread AX rule is stale. Parallel writes can still hold a frame schedule open; responsiveness needs measurement before adopting the engine. Edge parking and adjacent displays need physical testing.

OmniWM

3,375 stars

Swift / AppKit / SwiftUI · GPL-2.0-only

A substantial native scrolling implementation, also offering a BSP layout. Its per-application AX workers accept batched frame requests; mailboxes replace pending work by window ID and generation checks cancel stale writes. Viewport motion separates gesture, spring and deceleration states.

Its broad feature set adds integration surface. Use as a reference for Mac behavior and asynchronous frame delivery. Evaluate the GPL distribution model before choosing it as the product's code foundation.

Defi

34 stars

Swift · MIT

An emerging scrolling manager with a useful separation between pure layout, runtime intent and Mac frame delivery. Its AX coordinator rejects stale generations, rebases animation onto completed positions and keeps display callbacks separate from AX writes.

Small adoption compared with the established projects. Its performance document includes historical measurements and later revalidation that did not establish a general gain. Trackpad navigation is outside its documented V1 scope. Treat its targets as targets, not benchmark guarantees.

glide

694 stars

Rust / AppKit · MIT OR Apache-2.0

Strong separation between system wrappers, pure model and side-effecting actors. Per-application threads handle AX work; transaction IDs keep delayed feedback from undoing newer intent. Animation requests can replace an active animation.

Its main layout model is a tiling tree, so adopting it would require scrolling behavior. Its actor design is more relevant here than copying its complete layout engine. Package metadata explicitly offers a dual license.

03 / Recommended structure

Keep desired layout separate from observed windows.

Native appSwiftUI + AppKit

Settings, permission guidance, status menu, shortcut recorder, launch at login and engine lifecycle. Sends configuration and commands through local IPC.

Background engineRust, or Swift for a single-language build

One canonical layout state → column and viewport geometry → display-synchronized motion → bounded per-application AX workers. Generation IDs retire stale commands and observed-frame feedback confirms the accepted result.

macOS + other appsAX / display and workspace events

May respond late, reject a size, replace a window handle or move an off-screen window. Observations reconcile back into the engine rather than becoming a second independent layout authority.

Isolate slow applications

Glide and AeroSpace use application-specific AX threads. OmniWM's per-window mailboxes replace pending requests; Defi tracks generations and completed frames. Adopt bounded, replaceable work and keep blocking AX out of input callbacks.

Plan around parking

Paneru and PaperWM.spoon retain a visible sliver because fully off-screen frames can be reassigned or constrained. Nehir documents multi-monitor bleed. Test side-by-side displays, mixed scaling, Dock edges and native Spaces before promising seamless behavior.

Animate one coherent viewport

Use a shared monotonic timeline and display callbacks that schedule work. Do not let delayed callbacks queue obsolete frames. Niri supplies behavior; Rift and Defi supply Mac scheduling examples. Support interrupted gestures and reversals.

Respect human focus

Clicks, Command-Tab and Dock actions must reconcile with keyboard navigation. A background dialog or late AX notification must not unexpectedly scroll the strip. Keep transient ownership and minimum-size exceptions explicit.

For the initial product, target SIP-enabled operation and use public AX frame writes as the baseline. Several candidate engines still use undocumented APIs for identification, notifications, gestures or workspace information. “SIP enabled” does not establish “public APIs only.”

04 / Feasibility and delivery

The strip is the small part. Reliability is the product.

Build sliceConcrete resultWhat proves it works
Engine feasibilityDiscover windows, keep widths, focus left/right, scroll one display, float unsuitable windows, restore positions on graceful exit.Safari, Terminal, Finder and an Electron app; rapid commands and one slow target app; no focus loops or stranded windows.
InteractionTrackpad motion, interrupted spring animation, stacks/tabs, widths, drag reordering and multi-display routing.Gesture reversals, many windows, modal dialogs, fixed-size windows, horizontal monitor layouts and mixed refresh rates.
App experienceNative settings, onboarding, permissions, hotkeys, durable layout, launch at login and diagnostics.Clean install, configuration changes while active, restart, sleep/wake, display disconnect and native fullscreen transitions.
DistributionSigned app and helper, notarized package and updates under a distinct product identity.Install/update/relaunch on a clean Mac with stable permission behavior and compatible bundled dependencies.

The existing engines make this buildable without inventing every Mac workaround. A reliable parity estimate depends on the engine evaluation and agreed feature scope; this study does not establish a delivery date.

Recommendation: Rust engine + SwiftUI/AppKit shell, with Paneru as the first engine candidate and Rift as the second. Use Glide's isolation and consistency model as an architectural reference. If starting completely fresh, Swift throughout is the simpler default until profiling identifies a reason to split languages.

05 / Provenance

What was actually checked.

Architecture-focused source inspection of 17 public repositories, selected for direct scrolling relevance, Mac adoption, platform techniques and lineage. Popularity was checked with live GitHub star counts; small emerging projects are included for technical relevance. This is not an exhaustive census or full audit of every file. This architecture-study phase did not build, install or benchmark upstream projects; subsequent engine evaluation is recorded separately.

Every expanded project entry links to actual source files at an exact Git commit. License labels were reconciled with checked-in text where GitHub returned NOASSERTION or incomplete metadata. These are repository observations; any adopted code and dependencies still need a scoped distribution review. GPL projects remain useful behavioral references even when a permissive foundation is preferred.

The product description comes from ChainYourMac; gesture conflicts come from its setup guide. Platform conclusions also use the source implementations above. No proprietary implementation, binary reverse engineering or installed-app tests were used.

Claims about smoothness, CPU usage and superiority require comparable measurements. A useful matrix is 1/10/30 windows, fast and slow target apps, 60/120 Hz, one/two displays, navigation bursts, and recovery events. Measure planning, first write, observed convergence, focus latency, idle wakeups and CPU separately. An AX observation timestamp is not input-to-photon latency.
